# DUT Comparison Demonstration

This document is the short presentation script for the three RTL versions.
Run all commands from the repository root.

## 1. Original Supplied Source

```sh
make -C sim original
```

Expected result: compilation fails before simulation.

Reason: `ALU.sv` uses `clk` and `rst` in `always_ff`, but neither signal is
present in the module port list. The testbench cannot legally connect or drive
those signals until the DUT interface is completed.

## 2. Clock/Reset-Completed Buggy DUT

```sh
make -C sim buggy
```

Expected result: the DUT compiles, and the scoreboard reports 3 failures and
5 passing checks in the directed regression.

The interface repair makes simulation possible, but does not repair behavior.
The failures expose the supplied signed arithmetic error logic:

| Inputs | Expected | Buggy DUT | Finding |
|---|---|---|---|
| `A=-1743747895`, `B=3599965031`, addition | Wrapped result, `Error=1` | Same result, `Error=0` | Missed signed overflow |
| `A=32'h7fffffff`, `B=32'd1`, addition | `32'h80000000`, `Error=1` | `32'h80000000`, `Error=0` | Missed signed overflow |
| `A=32'h80000000`, `B=32'd1`, subtraction | `32'h7fffffff`, `Error=1` | `32'h7fffffff`, `Error=0` | Missed signed underflow |

The first random-looking vector is generated by the existing directed sequence;
the two boundary vectors are the explicit corner cases.

## Constrained-Random Evidence

The ordinary random test generates 500 broad transactions, but exact boundary
values are unlikely to occur by chance. The constrained-random test closes that
gap without hard-coding every transaction:

| Scenario | Transactions | Constraint purpose |
|---|---:|---|
| Legal operations | 100 | Random operands with opcodes `000` through `100` |
| Reserved operations | 100 | Random operands with opcodes `101` through `111` |
| Addition error cases | 200 | Positive and negative signed overflow regions |
| Subtraction error cases | 200 | Both opposite-sign overflow regions |
| Logical operations | 100 | Random operands with AND, OR, and XOR |
| Safe arithmetic | 100 | Bounded operands that cannot overflow |

Run it with:

```sh
make -C sim constrained
```

The corrected DUT passes 800/800 checks. Running the same test with
`DUT=buggy` produces 279 scoreboard failures, proving that the constraints find
behavioral differences rather than only increasing transaction count.

## 3. Corrected DUT

```sh
make -C sim correct
```

Expected result:

```text
8 PASS
0 UVM_ERROR
0 UVM_FATAL
```

The corrected DUT:

- Treats both arithmetic operands as signed 32-bit values.
- Detects addition overflow when operands have the same sign and the result
  changes sign.
- Detects subtraction underflow when operands have different signs and the
  result sign differs from operand `A`.
- Clears `Error` for every valid operation before evaluating the opcode.
- Still reports `Error=1` for reserved opcodes.

## 4. Coverage Demonstration

```sh
make -C sim coverage DUT=correct
make -C sim report
```

The shorter equivalent is:

```sh
make -C sim coverage-correct
make -C sim report
```

The corrected DUT coverage result is:

- Functional coverage: `100.00% (89/89)` gradeable bins.
- DUT block coverage: `100.00% (9/9)`.
- The current IMC summary also reports a `101/102` RTL metric for the DUT;
  inspect the generated report's metric headings when presenting this value.

Functional coverage is not the same metric as RTL code coverage. The remaining
code-coverage holes are reported rather than hidden. A coverage review should
explain whether each hole is unreachable, reset-only, or requires more stimulus.

## Client Answer Format

For any question such as “what happens for these values?”, show:

1. The input values and opcode.
2. The expected arithmetic or bitwise calculation from the specification.
3. The expected `Result` and `Error`.
4. The actual DUT values from the monitor.
5. The scoreboard PASS/FAIL result.
6. A waveform around the active clock edge when timing matters.
